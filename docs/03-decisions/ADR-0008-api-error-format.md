# ADR-0008: API 에러 응답 공통 형식

> 상태: 승인 · 날짜: 2026-11-27 (사용자 승인 2026-11-27)

## 배경 (Context)
- SPA는 서버 오류를 입력란 옆에 보여줘야 한다(AC-001-2 "비어 있는 항목 옆에 오류 메시지", AC-005-3 "이미 1부 기록이 있습니다", AC-008-7).
- 같은 400이라도 원인이 여러 가지라서 상태 코드만으로는 분기할 수 없다. 409(중복 라운드·중복 골프장 이름), 422(나인추가 규칙·숨긴 골프장)도 마찬가지다.
- NestJS 기본 에러(`{ statusCode, message: string | string[], error }`)는 `message`가 문자열일 때도 있고 배열일 때도 있다. 필드 이름이 따로 없고 영어 문장이다.
- 사용자에게 보여줄 문장은 한국어여야 하고, 500에서 내부 정보가 새면 안 된다.
- 다른 사용자 리소스의 응답은 "없음"과 구분되면 안 된다(NFR-003, ADR-0005, `api-spec.md` §3).

## 선택지 (Options)
| 선택지 | 장점 | 단점 |
|---|---|---|
| A. NestJS 기본 형식 그대로 | 추가 코드 없음 | 모양이 일정하지 않음. 필드 단위 오류 없음. 영어 메시지. 분기용 코드 없음 |
| B. RFC 9457 Problem Details (`application/problem+json`, `type`·`title`·`status`·`detail` + 확장 필드) | 표준이라 포트폴리오 설명에 좋음. 도구 지원 | `type` URI를 문서로 관리해야 함. 필드 단위 오류는 어차피 확장 필드로 직접 정의. 이 규모에서는 필드가 많음 |
| **C. 자체 형식 `{ error: { code, message, fields?, requestId } }`** | 프론트가 쓰기 쉬움(`code`로 분기, `message` 그대로 표시, `fields`로 입력란 표시). 공유 타입 하나로 끝 | 비표준. 다른 시스템과 연동할 일이 생기면 변환 필요 |

## 결정 (Decision)
**C. 자체 형식**을 쓴다. 상세는 `api-spec.md` §2.2·§2.3.

```json
{ "error": { "code": "DUPLICATE_ROUND", "message": "이미 1부 기록이 있습니다.", "fields": [{ "field": "slot", "code": "DUPLICATE_ROUND", "message": "…" }], "requestId": "…" } }
```

- `code`: 대문자 스네이크, `api-spec.md` §2.3 목록에 있는 값만. 프론트는 이 값으로만 분기한다.
- `message`: 사용자에게 보여줄 한국어. 500은 고정 문구.
- `fields`: 입력란 단위 오류(400·409·422에서 원인이 특정 필드일 때).
- `requestId`: `X-Request-Id` 헤더와 같은 값. 로그 추적용.
- 타입은 `packages/shared/src/api/error.ts`에 한 번만 정의한다. 응답은 NestJS 전역 예외 필터 한 곳에서만 만든다.
- 상태 코드 구분: 400 형식·범위 / 401 미인증 / 403 요청 출처(Origin·프록시 비밀) / 404 없음 또는 남의 것 / 409 유니크 충돌 / 422 업무 규칙.

## 근거 / 결과 (Consequences)
- 좋은 점: 화면 코드가 단순해진다(에러 처리 함수 하나). 공유 타입이라 오타가 컴파일 오류로 잡힌다. 남의 리소스와 없는 리소스의 응답을 `requestId` 말고는 똑같이 만들기 쉽다.
- 감수할 점: 표준(RFC 9457)이 아니다. 필요해지면 필드 이름을 1:1로 옮길 수 있다(`code` → `type` 끝부분, `message` → `detail`, `fields` → `errors`).
- 해야 할 일: E2E 테스트에서 모든 4xx 응답이 이 스키마에 맞는지 검사한다(`api-spec.md` §11).
