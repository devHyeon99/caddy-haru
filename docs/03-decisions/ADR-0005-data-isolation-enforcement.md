# ADR-0005: 사용자별 데이터 분리 강제 — Repository 명시적 userId + DB 복합 FK

> 상태: 승인 · 날짜: 2026-11-27

## 배경 (Context)
- **NFR-003**(Must): 사용자는 자기 라운드·골프장만 조회·수정할 수 있어야 하고, 다른 사용자 데이터에는 어떤 경로로도 접근할 수 없어야 한다. 서버 측에서 강제한다.
- **AC-N003-1**: B가 A의 ID로 조회·수정·삭제를 직접 요청하면 거부된다. 자동화 테스트로 검증한다.
- **AC-N003-2**: 목록·달력·통계·CSV에 다른 사용자 데이터가 섞이지 않는다.
- ADR-0002 규칙 5: Repository 계층에서 사용자 ID 조건을 강제한다.
- ORM은 아직 정하지 않았다(ADR-0003 예정). 그래서 이 결정은 특정 ORM 기능에 의존하면 안 된다.

## 선택지 (Options)
| 선택지 | 장점 | 단점 |
|---|---|---|
| **A. 명시적 userId** — 모든 Repository 메서드가 `userId`를 첫 인자로 받고 쿼리에 `user_id` 조건 | 코드만 읽어도 보임. 테스트하기 쉬움. ORM과 무관. Spring으로 옮기기 쉬움 | 메서드마다 인자 하나가 늘어남. 빠뜨리면 사람이 실수할 수 있음 → 타입·테스트로 보완 |
| B. 요청 컨텍스트(AsyncLocalStorage/CLS) 자동 주입 | 반복 코드 적음 | 동작이 숨겨져 있어 처음 배우는 사람이 추적하기 어려움. 백그라운드 작업·테스트에서 컨텍스트가 비면 사고 위험 |
| C. Postgres RLS 추가 | DB가 마지막 방어선 | 트랜잭션마다 `SET`이 필요하고 Neon 풀링(PgBouncer transaction 모드)·ORM과 조합이 까다로움. 1개월 일정에 과함 |

## 결정 (Decision)
**A를 채택하고, DB 제약으로 한 겹 더 막는다.** (사용자 선택, 2026-11-27)

1. userId는 **세션에서만** 나온다(`@CurrentUser()`). DTO에 userId 필드 없음, `forbidNonWhitelisted`.
2. 사용자 소유 데이터의 Repository 메서드는 모두 `userId: UserId`(브랜드 타입)를 첫 인자로 받는다. userId 없는 `findById(id)`는 만들지 않는다.
3. 단건 조회·수정·삭제는 `WHERE id = ? AND user_id = ?`. 0행이면 404 — 남의 데이터와 "없음"을 구분하지 않는다.
4. DB: `golf_clubs UNIQUE (id, user_id)`, `rounds (golf_club_id, user_id) → golf_clubs (id, user_id)` 복합 FK, `user_id NOT NULL`.
5. 테스트: 격리 E2E(B → A의 ID: 404, A 데이터 불변), **`:id` 라우트 누락 감지 테스트**(표에 없는 라우트가 있으면 실패), Repository 통합 테스트, FK 제약 테스트. 상세는 `architecture.md` §3.3.

## 근거 / 결과 (Consequences)
**좋은 점**
- 규칙이 눈에 보이고, 타입(`UserId`)·리뷰 체크리스트·라우트 누락 테스트가 실수를 잡는다.
- 코드에 버그가 있어도 복합 FK가 "남의 골프장을 내 라운드에 연결하기"를 DB 차원에서 막는다.
- ORM(ADR-0003) 선택과 무관하다. ORM을 고를 때 "복합 FK를 표현할 수 있는가"를 평가 기준에 넣는다.

**감수할 점**
- 집계·CSV 같은 직접 쿼리에서도 user_id 조건을 사람이 넣어야 한다 → AC-N003-2 교차 검사 테스트로 보완.
- RLS를 쓰지 않으므로 DB에 직접 접속하는 도구(마이그레이션, 백업)는 전체 데이터를 본다. 이 접속 정보는 GitHub Secrets에만 둔다.

**다시 검토할 조건**
- 사용자가 크게 늘거나, 서버 밖(관리 도구 등)에서 DB를 직접 읽는 경로가 생기면 C(RLS) 추가를 검토한다.

## 변경 이력
- 2026-11-27 작성·승인 (사용자 선택: 명시적 userId)
